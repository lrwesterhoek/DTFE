VERSION 1.3.0
- Added Phase-Space DTFE (PS-DTFE), enabled by the '-DPHASE_SPACE' compile flag and built with the new 'make PS-DTFE' target (separate executable; object files in /o_ps). The Delaunay tessellation is built in Lagrangian (initial-condition) space and the density of each vertex is estimated as the ratio of its Lagrangian to Eulerian simplex volume. Grid interpolation iterates over all Delaunay cells and accumulates the contributions of every Eulerian simplex overlapping a grid point, so multi-stream regions are handled correctly. Defined in "src/CGAL_triangulation/ps_interpolation.cc" with supporting code in triangulation.cpp, DTFE.cpp and vertexData.h.
- PS-DTFE reads two positions per particle: the Eulerian 'Coordinates' and the Lagrangian 'InitialCoordinates' from a gadget HDF5 file (input type 105). If 'InitialCoordinates' is absent, the Lagrangian positions can be supplied from a separate initial-conditions HDF5 file via the new option '--lagrangianInput', matched to the main file by 'ParticleIDs'. PS-DTFE input is HDF5-only.
- Added a new output field, "<output>.streams", giving the number of streams at each grid cell (PS-DTFE only).
- Unsupported-in-PS-DTFE combinations now exit with an explanatory message: volume-averaged ('_a') fields, redshift-cone grids and user-defined sampling points.
- Added a build + run smoke test: "tests/ps_smoke_test.sh" builds PS-DTFE, generates a synthetic Zel'dovich-pancake snapshot ("tests/generate_ps_test_data.py") with genuine shell crossing, runs the executable, and verifies that the density and stream-count outputs are finite, non-negative, roughly mass-conserving and multi-stream. See the README section "Phase-Space DTFE (PS-DTFE)" for usage.
- Added an analytic regression test: "tests/ps_regression_test.py" compares the PS-DTFE pancake output against the exact 1-D Zel'dovich solution (three-stream volume fraction, Eulerian caustic positions, and stream counts inside/outside the multi-stream slab) and regression-checks tracked metrics (grid mass / expected mass, multi-stream fraction, maximum stream count) against a baseline in "tests/reference/ps_regression_baseline.json".
- Fixed a PS-DTFE grid-interpolation bug that left roughly half of all grid cells empty (mass deficit ~45%). The point-in-simplex test in "src/CGAL_triangulation/ps_interpolation.cc" computed barycentric coordinates as Ax^-1 * rel, but the cell edge matrix Ax stores edge vectors as rows, so the correct expression is (Ax^-1)^T * rel. The missing transpose made the test reject ~96% of interior grid points; with it, single-stream regions are fully covered (grid coverage ~100% and mass conservation is restored to point-sampling accuracy). The density/velocity gradients use Ax^-1 directly and were already correct.
- PS-DTFE velocity/scalar fields are now the mass-weighted mean over streams in multi-stream regions, <f> = sum(rho_s f_s)/sum(rho_s), accumulated density-weighted during the scatter and normalized by the summed stream density afterwards. Single-stream regions are unchanged. Previously these fields were a raw sum over streams and were only meaningful where streams=1.
- PS-DTFE now supports volume-averaged ('_a') fields (previously a hard error). Each grid cell is sampled on an nSub^NO_DIM regular sub-grid (nSub=3) and the field is volume-averaged; multi-streaming is handled by the same cell iteration. This enables density_a, velocity_a, etc. in phase-space mode and reduces the point-sampling mass deficit. interpolateGrid_phaseSpace() now takes the target Field and a sub-sample count (nSub=1 reproduces the unaveraged cell-centre result exactly).
- PS-DTFE is now parallelized COARSE-GRAINED over Lagrangian partitions (enable with --partition, e.g. 2 2 2), mirroring how the standard DTFE parallelizes over spatial partitions in DTFE_parallel: the Lagrangian-partition loop runs under '#pragma omp parallel for', each thread builds its own Delaunay triangulation for one partition and interpolates it, and the per-partition grids are summed into the shared output under a critical section. The per-cell scatter inside interpolateGrid_phaseSpace is therefore SERIAL. (A fine-grained per-cell parallel scatter -- both an atomic and a per-thread-buffer variant -- was implemented and measured first; it is memory-bandwidth bound and did not speed up, so it was removed in favour of this coarse-grained scheme.) Peak memory is ~ (#partitions run concurrently) x full grid, since each Lagrangian partition writes the whole Eulerian grid; reduce the partition count if memory-limited. Correctness (parallel == serial: unaveraged integer stream counts exactly, averaged stream count and float fields within rounding) is checked by tests/ps_parallel_check.sh, and the Zel'dovich regression test exercises '--field density velocity density_a' including the mass-weighted velocity and averaged density.
- Fixed a PS-DTFE partition-path crash (EXC_BAD_ACCESS in Quantities::addFrom) hit by any run that combines an averaged ('_a') field with '--partition', e.g. '--field density velocity density_a --partition 2 2 2'. interpolateGrid_phaseSpace always emits a stream_count for whichever quantities it fills, but in the partition path only the unaveraged accumulator (uQuantities) had its stream_count pre-sized -- the averaged accumulator (aQuantities) did not -- so summing the non-empty per-partition stream_count into the empty shared vector wrote past its end. Both shared stream_count accumulators are now pre-sized whenever their interpolation pass runs (uField/aField selected), and Quantities::addFrom additionally grows an undersized destination (zero-filled) as a safety net. The same gap would also have crashed '--field velocity --partition' (no density). Reproduced at OMP_NUM_THREADS=1, confirming it was a missing allocation, not a data race.
- PS-DTFE '--partition' now reports a single AGGREGATE coverage/stream line instead of one misleading per-partition line. Each partition spans only ~1/Npartitions of the Eulerian grid, so the old per-partition "grid coverage ~12.5%" line (printed by the master thread) read as a bug. The per-partition stats are now suppressed in the partition path (new runtime-only flag User_options::psSuppressGridStats), and after the partition loop DTFE.cpp prints one total computed from the summed shared grid: aggregate max streams, multi-stream grid points, and covered/total cells. Non-partition runs are unchanged (still print the per-call stats).
- Added "tests/ps_scaling_benchmark.sh": a PS-DTFE strong-scaling benchmark that runs the same problem at 1/2/4/8 OpenMP threads (capped at the core and partition counts) and prints a wall-time / speedup / efficiency table. It doubles as a TRACKED scaling-regression guard -- it fails if the speedup at the top core count falls below MIN_EFFICIENCY x cores (default 0.4), catching a future change that accidentally serializes the partition loop. Measured on a 10-core Apple Silicon laptop (N=48^3, grid=96^3, --partition 2 2 2, --field density velocity density_a): 1 core 24.0 s (1.00x), 2 cores 12.3 s (1.95x), 4 cores 6.37 s (3.78x), 8 cores 3.63 s (6.63x) -- i.e. 83-100% parallel efficiency, near-linear up to the 8 partitions.
- Documented the PS-DTFE '--partition' memory model in the README (new "Parallelization, scaling, and memory" subsection) and in the '--partition' '--help' text (PHASE_SPACE-gated, so the standard DTFE help is unchanged): each Lagrangian partition writes the whole Eulerian grid, so peak memory ~ (concurrently running partitions) x full grid x number of fields. Pick the partition count from the core budget AND available RAM. (The structural fix -- restricting each partition to the Eulerian bounding box it touches -- is tracked as Tier 3.1.)
- Fixed a PS-DTFE correctness bug in the '--partition' path: the mass-weighted fields (velocity, velocity_gradient, scalar) were combined incorrectly across partitions in multi-stream cells. Each partition normalized its own mean <f>_p = sum_p(rho f)/sum_p(rho) and addFrom then SUMMED those means, but sum_p(<f>_p) != sum_all(rho f)/sum_all(rho) -- averaging is non-linear, so the result was only right where a cell is touched by a single partition. In multi-stream Eulerian cells that draw streams from several Lagrangian partitions the velocity was wrong by order unity (rel ~1.8 on the Zel'dovich pancake). Density and stream counts are linear and were already correct. Fix: the partition path now keeps the density-weighted MOMENTS un-normalized (new runtime flag psDeferNormalization), sums them and the per-cell mass weight sum(rho_s) linearly across partitions, and normalizes ONCE afterwards (Quantities::normalizePhaseSpace). Partition output now matches the single-tessellation result to float precision in both single- and multi-stream cells. The bug was masked because the regression test is non-partition and the parallel check only compared partition-vs-partition; it is exactly what the standard-DTFE cross-check (Tier 4.3) targets.
- Added the PS-DTFE mass-weighted velocity DISPERSION, the signature phase-space observable for void work ('--field dispersion' / 'dispersion_a'). It is the full symmetric tensor sigma_ij = sum(rho_s (v_s,i-<v>_i)(v_s,j-<v>_j))/sum(rho_s) = <v_i v_j>-<v_i><v_j>, accumulated as the density-weighted second moment in the same cell scatter as the velocity. Writes the trace sigma^2 (the velocity "temperature") to "<output>.velDisp" and the full tensor (upper-triangle row-major, 6 components in 3D) to "<output>.velDispTensor", plus their '_a' volume-averaged versions. ~0 in cold single-stream regions (void interiors), large in multi-stream regions (walls/filaments). Validated on the Zel'dovich pancake against the analytic three-stream dispersion: slab-centre sigma^2 matches to ~0.2% and single-stream cells are 0 -- now a tracked check in tests/ps_regression_test.py. Diagonal components (variances) are clamped >=0. Correct in both the serial and '--partition' paths.
- Added a PS-DTFE vs standard-DTFE single-stream cross-check (Tier 4.3), tests/ps_standard_cross_check.py: runs both codes on the same pancake and compares where streams==1. The velocity matches tightly (~4e-6 median rel) -- both interpolate the same particle velocities linearly, so the result is nearly tessellation-independent in single-stream regions -- while the density matches only to estimator accuracy (~7% profile): density ~ 1/volume is sensitive to simplex shape and the two tessellations differ (regular Lagrangian vs stretched Eulerian), with standard DTFE additionally contaminated near the caustic. The two also use different density normalizations (standard ~mean 1, PS physical N*m/L^3), so densities are compared after dividing by their own mean.
- Strengthened the PS-DTFE regression test: a HARD mass-conservation assertion (grid mass / expected within [0.90,1.15], absolute, independent of the tracked baseline; Tier 4.2); a stream-count PARITY assertion (the count is odd -- 1 or 3 -- away from caustics, even only in the thin caustic-boundary cells; Tier 1.4); and the velocity-dispersion analytic check noted above. Verified that '--field gradient' (velocity gradient) already works in PS mode and matches standard DTFE to ~5e-8 in single-stream cells (Tier 1.2).
- README PS-DTFE section brought fully in sync (Tier 5.1): a field/output table (--field -> files, component counts, meaning), the volume-averaged '_a' forms, recommended grid settings, and an honest limitations list -- including the resolution-dependent mass conservation on caustic-rich fields (the unaveraged density is point-sampled at cell centres, so the integrated mass varies by ~+-10% between grid 64/96/128; density_a is steadier), the non-periodic path being unvalidated, and 2D being untested.
- Added run_ps_dtfe.sh, the PS-DTFE counterpart of run_dtfe.sh (config block + snapshot loop), and tests/plot_ps_dtfe.py to visualise the output fields (2D slices + 1D profiles).
- Robustness pass (Tier 2): NON-periodic PS-DTFE now emits a clear warning -- its convex-hull trimming (correct for periodic boxes) discards the genuine surface of a finite cloud, so a centred-clump test recovered only ~20% of the mass; use --periodic (Tier 2.1). Anisotropic grids (--grid nx ny nz, nx!=ny!=nz) verified correct via the per-dimension dx/bbox math (Tier 2.4). Velocity normalization confirmed consistent with standard DTFE in single-stream regions (Tier 2.2, via the cross-check). Added a compile-time #warning that the NO_DIM==2 PS path is untested (Tier 2.5).
- Added a genuinely 3D analytic test, tests/ps_3d_test.py (Tier 4.1): three crossed Zel'dovich waves give a separable map whose stream count is the product of the per-axis counts, so it takes values {1,3,9,27} with multi-stream fraction 1-(1-f)^3 and max 27. PS-DTFE reproduces this (100% of covered cells land on {1,3,9,27}, multi-fraction and mean within tolerance). generate_ps_test_data.py gained '--crossed-waves' (3D displacement) and '--margin-frac' (a non-periodic clump in vacuum).
- Extended the regression baseline with velocity/dispersion metrics (Tier 4.5): peak |v_x| and the median dispersion inside the 3-stream slab are now tracked (existing density/stream metrics unchanged). README gained a performance/averaging-cost note (Tier 3.3).
- Added a PS-DTFE convergence test, tests/ps_convergence_test.py (Tier 4.4): the single-stream density profile converges to the analytic Zel'dovich solution 1/|1+A k cos(k q)| as particle number grows (L1 error 0.0040 -> 0.0012 over N=48/64/96^3 at fixed grid). Uses the no-partition path (the partition path adds a small partition-boundary floor that would mask the trend). The multi-stream FRACTION, by contrast, is grid-discretisation-limited (set by which cells fall in the slab), not particle-limited -- documented rather than convergence-tested.
- Implemented the per-partition sub-grid memory optimisation (Tier 3.1). Each partition now allocates only the Eulerian bounding box of the grid cells it touches, not the whole grid: a cheap first pass over the kept cells (same filtering/bounding box as the scatter) marks, per axis, which grid planes are overlapped, giving a box [subOrigin, subOrigin+subDims); axes whose touched set reaches both ends (a fold or periodic wrap) stay full. The per-partition interpolation fills this box (Quantities::ps_subOrigin/ps_subDims), and the new Quantities::addFromSubgrid maps it back into the full shared grid. On the pancake a half-box partition occupies ~15% of the grid; measured peak RSS dropped ~2.6x (4.16 -> 1.58 GB at grid 192^3, --partition 2 2 2, 8 threads) with output verified BIT-IDENTICAL to the full-grid path (1-thread, all fields). Peak memory is now bounded by the concurrent thread count, not the total partition count. (Note: User_options/Quantities gained members, so a clean rebuild is needed -- the Makefile does not track header dependencies.)
- Fixed the non-periodic path (Tier 2.1) -- a finite particle cloud in vacuum now conserves mass (~0.96-1.02 across grids, was ~0.20). Two causes were addressed: (1) the density normalization used the BOX volume (N*m/L^3), but the PS vertex density is avgDensity*V_Lag/V_Eul, so for a cloud filling a fraction f of the box the mass came out a factor f too low; for a non-periodic isolated cloud (no --periodic, no --region) avgDensity is now the cloud's LAGRANGIAN mean N*m/V_lagBox (exact for a regular IC grid, where the Lagrangian bounding box is the tessellated convex hull). (2) the convex-hull boundary cells were culled as a periodic artefact; for non-periodic they are now KEPT, with a constant density from their own |det(Lagrangian edges)|/|det(Eulerian edges)| volume ratio, recovering the cloud's surface layer. The periodic path is unchanged (the cull still applies; regression/parallel/3D/smoke bit-for-bit identical). Validated by tests/ps_nonperiodic_test.py. Caveat: assumes a roughly convex, regular Lagrangian distribution (standard DTFE convex-hull assumption); feeding periodic data without --periodic is still wrong.
- Implemented CGAL TBB parallel triangulation (Tier 3.2) as an OPT-IN build, `make PS-DTFE TBB=1` (or DTFE TBB=1): the single global tessellation (the no-`--partition` path) is built with CGAL's parallel insertion -- a Parallel_tag triangulation data structure, a Spatial_lock_grid lock structure, and a range insert of (point, info) pairs that runs insert_with_info under tbb::parallel_for. Gated behind -DPARALLEL_TRIANGULATION so the default builds are byte-for-byte unchanged (the sequential path moved into an #else; verified the full suite still passes without TBB). Requires `brew install tbb`. Output verified correct (the Delaunay triangulation is unique, so the regression test passes with the TBB build).
  HOWEVER -- benchmarking shows it is ~2x SLOWER than the sequential build at tested scales (1.48M pts: 5.2s seq vs ~10-13s parallel; 3.5M pts: 12.5s vs 25.3s), the gap not closing with N. Two reasons: the parallel path cannot use CGAL::Fast_location (a sequential point-location hierarchy) which the sequential build relies on, and CGAL's parallel insertion overhead (lock-grid contention on the grid-structured + periodic-copy point distribution) outweighs the ~3x core utilisation it achieves. CGAL parallel Delaunay is tuned for much larger, more uniform point sets (tens of millions+); at PS-DTFE's scales and distribution it does not pay off. The '--partition' path remains the recommended parallelisation (it parallelises BOTH the triangulation and the interpolation per partition, ~6.3x at 8 cores). Kept as an honest, opt-in option for the very-large-N many-core regime.
- The averaged ('_a') PS-DTFE stream count is now written to "<output>.a_streams" (the per-cell average number of streams), alongside the existing unaveraged "<output>.streams".
- The near-singular cell-skip threshold in ps_interpolation.cc is now a named, documented constant (DEGENERATE_DET_TOL = 1e-6 * mean-edge^3): it drops only numerically zero-volume simplices, while genuine (finite-volume) caustic cells are retained.
- Added "tests/ps_parallel_check.sh": runs the same problem with OMP_NUM_THREADS=1 and with all cores and verifies the outputs agree (unaveraged integer stream counts exactly; the averaged stream count and float fields within rounding, since cross-partition summation order differs) to catch any parallel data race.
- Fixed two related PS-DTFE periodic-copy issues: (1) Lagrangian periodic copies are now shifted by the box period (eulerLen) instead of the particle bounding-box width, which previously placed copies on top of boundary originals; (2) the de-duplication of periodic images now keeps the cell whose Lagrangian centroid lies in the primary box, instead of testing the (arbitrarily ordered) vertex 0. Added a "grid coverage" line to the PS-DTFE output to flag any uncovered cells.
- Build fixes for current macOS toolchains (Homebrew LLVM + recent Xcode/Boost): the Makefile now auto-detects a valid macOS SDK and passes it as -isysroot to every compile rule (including the kdtree2 rules, which previously bypassed the shared flags), avoiding the "no such sysroot directory .../MacOSXNN.sdk" failure; override with 'make ... MACOS_SDK_OVERRIDE=/path/to/SDK'. Removed the stale '-lboost_system' link flag (Boost.System is header-only since Boost 1.69 and is no longer shipped as a library). These fixes apply to both the DTFE and PS-DTFE targets.
- Added a '--max-concurrent N' option (both DTFE and PS-DTFE) that caps how many Delaunay triangulations are built SIMULTANEOUSLY, to bound peak memory on machines with less RAM -- it trades CPU cores for memory; 0 (default) uses all threads, i.e. the previous behaviour. The concurrently-built triangulations are the dominant memory cost, so peak RAM ~ fixed(resident particles + output grids) + N x per-triangulation. In PS-DTFE it sets num_threads on the Lagrangian-partition loop (DTFE.cpp), so a finer --partition (smaller per-triangulation) plus a small --max-concurrent fits large grids in limited RAM; in standard DTFE it caps the concurrent spatial sub-triangulations inside DTFE_parallel. Numerically LOSSLESS: partitions are still summed under the same critical section and normalized once, so the fields are unchanged -- verified that --max-concurrent 1/4/8 produce identical output (integer streams exact, floats within rounding), tests/ps_parallel_check.sh stays PASS, ps_regression_test.py matches the baseline, and the standard suite is 10/10. Exposed in --help and printOptions; wired into run_ps_dtfe.sh (MAX_CONCURRENT=4, tuned so GRID 512 / --partition 4 4 4 with the density+velocity+dispersion field set fits a 64 GB machine, ~49 GB) and run_dtfe.sh (default 0).
- Restructured the terminal output for both DTFE and PS-DTFE into a colored, segmented, progress-reporting log:
  * SEGMENTATION: the run is now broken into '=== RUN CONFIGURATION ===', '=== READING INPUT ===', '=== DTFE COMPUTATION ===', '=== WRITING OUTPUT ===', '=== SUMMARY ===' banners (MESSAGE::banner(), printed from main.cpp + printOptions).
  * PROGRESS + ETA: every completed partition prints '[partitions K/N | P%]  elapsed Xs, ETA ~Ys' (so a long run is no longer a guessing game). Implemented in BOTH the PS Lagrangian-partition loop (race-free: counter + print inside the existing omp critical, timed with std::chrono::steady_clock) and the standard-DTFE serial --partition loop. The existing per-stage 'Done: N%' bars are unchanged.
  * SEMANTIC COLOURS: errors red, warnings yellow, stage timings + progress + 'Done' green, section banners / headers / aggregate-stats cyan, file paths blue, field/result values magenta, labels/keys dim-yellow. A small palette + helpers in src/message.h (cRed/cYellow/cGreen/cCyan/cBlue/cMagenta/cYellowD/cDim/cBold/cReset, banner(), hrule(), formatDuration()).
  * SUMMARY: prints peak RSS (magenta) and TOTAL WALL TIME (the binary now times itself with std::chrono, not just the run script).
  * Disambiguated the two identical 'interpolation to sampling points' timing lines into 'field interpolation (per-point / unaveraged)' and 'field interpolation (volume-averaged \'_a\')'.
  * GATING: all colour is emitted only when stdout is a real terminal (isatty) AND NO_COLOR is unset, evaluated once; suppressed when piped/teed to a file (the run script's .runlog) -- verified 0 ESC bytes piped, codes present under a pty, 0 with NO_COLOR=1. Output content/results unchanged; all tests pass (standard suite 10/10, ps_parallel_check PASS, ps_regression PASS).
- Fixed misleading per-stage timing: "  >>> Time: N sec." used CGAL::Timer (CPU time), so under the concurrent --partition loop it SUMMED across threads and grossly overstated wall time (a 14-min run printed "4013 sec" for the averaged-interp stage). Switched the Timer typedef to CGAL::Real_timer (wall clock) in CGAL_include_{3D,2D}.h and removed the now-wrong '/noProcessors' division in printComputationTime. Now reports real wall seconds; results unchanged (display-only; all tests pass).
- PS-DTFE printOptions no longer prints the standard Monte-Carlo averaging block ('volume averaging method' / 'number sampling points') nor the 'DUMMY TEST particles' line -- both unused in phase-space mode (which volume-averages on the nSub^NO_DIM sub-grid, reported as 'avg sub-samples (nSub)', and skips dummy-boundary insertion). Guarded with #ifndef PHASE_SPACE; standard DTFE unchanged. Softened the 'uncovered cells' wording (can be legitimate empty/expanding regions).
- Added '--avg-subsamples N' (PS-DTFE only, default 3): the linear sub-sample count nSub for the volume-averaged ('_a') fields. Each grid cell is volume-averaged over an nSub^NO_DIM regular sub-grid, and that averaged interpolation pass is the DOMINANT runtime cost of a PS-DTFE run (it iterates every Delaunay cell against nSub^3 sub-points per grid cell). Previously nSub was hardcoded to 3 (27 sub-points) in triangulation.cpp. Measured on the small parallel-check snapshot the averaged pass scales as nSub^3: nSub=3 -> 6.71 s, nSub=2 -> 2.15 s (8 sub-points, ~3.1x faster), nSub=1 -> 0.14 s (cell-centre only = the unaveraged value). Lower nSub trades a small amount of mass capture in PARTIALLY-COVERED cells (fewer sub-points sample less of a cell the tessellation only partly fills) for a large speedup; at production resolution (grid <= particle count) most cells are well covered so the difference is small -- check the printed 'density_a grid_mass/expected' stays near 1. Default 3 keeps existing behaviour/baselines unchanged (the regression and parallel tests, which don't pass the flag, are bit-identical). Wired into run_ps_dtfe.sh (AVG_SUBSAMPLES=2) and reported in printOptions. The unaveraged fields are unaffected (they are always cell-centre, nSub=1).
- PS-DTFE '--partition' periodic copies are now generated PER-PARTITION on the fly (new helper findParticlesInBoxLagrangianPeriodic in subpartition.h) instead of materializing the whole-box array of Lagrangian periodic images up front. That global copy array was held resident for the ENTIRE run (originals + ~1.2x N copies, ~14 GB at 512^3) even though each partition only needs the images overlapping its own padded slab. The partition path now keeps state.particles originals-only (~6.4 GB at 512^3) and each partition synthesizes just the images whose shifted Lagrangian position lands in its padded box -- the dominant fixed memory floor under the partition loop drops by ~8 GB, which directly lets more partitions run concurrently within a given RAM budget. Bit-for-bit identical to the old global-copy path: every partition's padded box is a subset of the global padded box (lagPadding <= lagPad by construction), so the deferred image set is exactly what the global build + selection produced -- confirmed by ps_parallel_check.sh (PASS) and ps_regression_test.py (matches the stored baseline exactly). The single-triangulation (no-'--partition') PS path still builds all images up front because one global tessellation needs them; standard DTFE is unchanged (its --partition path already generated periodic copies per-partition via findParticlesInBox).

      2 - read particle weights
      4 - read particle velocities
to read multiple data add the number corresponding to each data set, for example 3=1+2 - specifies to read only particle positions and weights/masses, while a value of 7=1+2+4 specifies to read positions, weights and velocities [ DEFAULT = 7 -read positions, weights and velocities ]
- added an additional third option after for the '--input' parameter which specifies for which gadget particle species to read the data. You can select the following:
      1 - read the data for gadget species 1 (normally gas particles)
      2 - read the data for gadget species 2 (normally dark matter particles) [DEFAULT]
      4 - read the data for gadget species 3 (usually stars or different mass DM particles in multiple resolution simulations)
      8 - read the data for gadget species 4
      16 - read the data for gadget species 5
      32 - read the data for gadget species 6
to read data for multiple species just add the number corresponding to each particle type, for example 7=1+2+4 - specifies to read the data for both particle types 1, 2 and 3.

- added the '--output' or '-o' option to specify the output file type. Available options:
      101 - the default binary output
      100 - binary file with my own custom header and file structure
you can set the default output file in the Makefile by changing the values assigned to the '-DOUTPUT_FILE_DEFAULT' option.

- added option '--resdhiftSpace' that can be used to tranform the particle positions from position-space to redshift-space. For the option to work you need to enable the '-DREDSHIFT_SPACE' option in the Makefile. Than you need to call the '--resdhiftSpace d1 d2 d3' during runtime with (d1,d2,d3) the direction along which to use the velocity for the transformation to redshift space. The (d1,d2,d3) direction will be normalized to a unit vector by the program!
